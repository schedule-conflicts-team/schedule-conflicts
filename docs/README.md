# Документация проекта

> Карта разделов документации и правила оформления файлов в `docs/` для проекта "Учебное расписание и конфликтология" (кейс №11).
> Связано: [Как работать с репозиторием](../CONTRIBUTING.md); [Карточка проекта](project/project-card.md)

## Разделы

- `analysis/` - продуктовое описание, акторы, границы системы, аналоги, требования MoSCoW, матрица трассируемости и диаграмма вариантов использования (`use-cases/`).
- `architecture/` - архитектура системы и подсистемы 1С, модель хранения данных, контракты обмена и диаграммы C4 (`c4-context/`, `c4-container/`, `c4-component-1c/`).
- `adr/` - архитектурные решения (ADR).
- `project/` - карточка проекта, роли и матрица RACI, roadmap, пакеты работ, план разработки, риски, реестр изменений (`change-requests.md`), поручения и протоколы встреч (`meetings/`).
- `testing/` - приёмочные сценарии и результаты проверок.

## Правила оформления

1. **Шапка документа.** Файл начинается с одного заголовка `# Название` без номеров версий (`v0.2` и т.п.) и цитаты `>` на 1-2 строки: краткое описание документа и при необходимости строка `Связано:` с относительными ссылками через `;`, без жирного выделения.

   Обычный документ:

   ```markdown
   # Название документа

   > Краткое описание в 1-2 предложения: о чём документ и что в него входит.
   > Связано: [Документ А](путь.md); [Документ Б](../папка/путь.md)
   ```

   Датированная запись (ADR, протокол встречи):

   ```markdown
   # ADR-0001: Название решения

   > Дата: ДД.ММ.ГГГГ; Статус: Принято
   > Связано: [Документ](../папка/путь.md)
   ```

   В обычных документах не указывать авторов, даты последнего обновления и таблицы истории версий - эти сведения хранит Git. В ссылках на другие документы не писать даты их редакций.

2. **Участники.** Во всех документах указывать GitHub-ник (`@epolykovskiy`, `@annsizova138-ship-it`, `@EllionorOstrom`, `@vovelio`, `@AlisnGol`). ФИО, учебная группа и Telegram-ник хранятся только в таблице команды в [карточке проекта](project/project-card.md). В матрице [RACI](project/raci.md) используются коды ролей `R1`-`R5`, а соответствие `@никам` приведено в таблице ролей в начале файла.

3. **Без временных статусов и разделов "Открытые вопросы".** Документы в `main` описывают только актуальное состояние и принятые решения. Не добавлять разделы "Открытые вопросы" / "Что уточнить", не ссылаться на открытые issues и не писать временные статусы ("открыта #N", "в работе", "начало работы неизвестно", "появится позже"). Текущие вопросы обсуждаются в PR или заводятся отдельными GitHub Issues.

   Исключения: ссылки на закрытые PR/Issue в [реестре изменений](project/change-requests.md) как основание принятого решения; статус прогона сценария в [приёмочных сценариях](testing/acceptance-scenarios.md).

4. **Единый источник правды.** Не копировать в другой файл состав MVP, роли, риски или модель данных - вместо пересказа ставить относительную ссылку на первоисточник.

5. **Относительные ссылки.** Для переходов внутри репозитория использовать рабочие относительные Markdown-пути. Не указывать текстовые имена старых файлов и ссылки на конкретные хеши коммитов (кроме явных архивных ссылок в `change-requests.md`).

6. **Имена файлов и диаграммы.** Новые файлы и папки называть латиницей в `kebab-case`. Диаграммы хранить в своей папке вместе с исходником `.puml` и экспортированными `.svg` и `.png` с одинаковыми латинскими именами.

7. **Базовый Markdown.** Один заголовок `#` на файл, последовательные уровни заголовков (`##`, `###`), без лишних горизонтальных разделителей `---` между разделами.

## Формат ADR

Новые архитектурные решения добавляются в `docs/adr/NNNN-slug.md` со следующими разделами:

- `## Контекст` - какая задача или ограничение требует решения;
- `## Решение` - принятый вариант и его границы;
- `## Альтернативы` - рассмотренные варианты и почему они не выбраны;
- `## Последствия` - плюсы, минусы и влияние на остальные части системы.
