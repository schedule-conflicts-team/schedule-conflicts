# Требования: цепочка и MoSCoW

Кейс 11 «Учебное расписание и конфликтология».

## 1. Цепочка «инсайт → потребность → требование → критерий»

| Этап | Формулировка | Результат |
|---|---|---|
| **Ц1. Роли и права** |  |  |
| Инсайт | В кейсе три роли: учебный отдел — создание расписания и просмотр конфликтов; преподаватель — просмотр личного расписания и уведомлений о конфликтах; администратор расписания — контроль исправлений и пересогласования. Для преподавателей нужен режим «только просмотр». Команда заменила роль «Преподаватель» публичным просмотром без входа: опубликованное расписание видят все, изменить его нельзя — это и есть режим «только просмотр». | Источник: кейс, разд. 2 п. 5, разд. 3 (Доступы); решение команды |
| Потребность | Учебному отделу и администратору нужны действия своей роли; преподавателям, студентам и всем остальным — видеть опубликованное расписание без учётной записи. | Роль: учебный отдел, администратор расписания, публичный просмотр (без входа) |
| Требование | Права ролей: учебный отдел работает с расписанием (загрузка, проверка, отчёт, экспорт; правка занятий в системе — во вторую очередь); администратор подтверждает публикацию и управляет учётными записями, сам расписание не загружает и не правит; без входа доступен только просмотр опубликованного расписания. | Т-01–Т-03 · Must; Т-69 · Should |
| Критерий | Под каждой ролью доступны только её действия; без входа открывается только опубликованное расписание, а черновик, загрузка, правка и публикация недоступны. | Проверка: вход под ролью, открытие без входа |
| **Ц2. Вход и учётные записи** |  |  |
| Инсайт | Кейс требует разграничения ролей. Команда решила сделать минимальную авторизацию. | Источник: кейс, разд. 3 (Доступы); решение команды |
| Потребность | Работать с расписанием должны только пользователи с учётной записью, каждый в рамках своей роли. | Роль: учебный отдел, администратор расписания |
| Требование | Вход по логину и паролю для учебного отдела и администратора; учётные записи создаёт администратор; при ошибке входа — сообщение; пароли хранятся в виде хэша; вход один раз; тестовые пользователи для каждой роли со входом. | Т-04, Т-06, Т-09 · Must; Т-05, Т-07, Т-08 · Should |
| Критерий | Без входа открывается только публичный просмотр; с неверным паролем вход не выполняется; паролей открытым текстом в базе нет; для каждой роли со входом есть тестовый пользователь. | Проверка: вход под ролью, просмотр базы |
| **Ц3. Загрузка CSV и дубли** |  |  |
| Инсайт | Расписание загружается из CSV. Повторный импорт CSV не создаёт дубликаты; повтор того же занятия в тот же момент не допускается. | Источник: кейс, разд. 1, разд. 2 п. 4, разд. 3 (Надёжность) |
| Потребность | Учебному отделу нужно загружать расписание из файла, в том числе повторно, без задвоения занятий. | Роль: учебный отдел |
| Требование | Загрузка расписания из одного CSV: строка — занятие, группы — в колонке group_ids через «\|»; повторная загрузка полностью заменяет черновик; дубль внутри файла — ошибка загрузки; частичное обновление по lesson_id. | Т-10, Т-11, Т-64 · Must; Т-12 · Could |
| Критерий | Тот же файл загружен дважды — число занятий не изменилось; после загрузки исправленного файла в черновике только занятия из него. | Проверка: тест на тестовых файлах |
| **Ц4. Проверка корректности данных** |  |  |
| Инсайт | Валидации кейса: start_time < end_time; все ссылки существуют; нет занятий вне рабочего окна. Каждая запись относится к одному преподавателю, аудитории и группе. Рабочее окно в кейсе не задано; продукт не привязан к одному вузу, поэтому сетку пар задаёт сам вуз. | Источник: кейс, разд. 2 п. 1 и п. 4; решение команды |
| Потребность | Учебному отделу нужно, чтобы некорректные занятия не попадали в базу, и знать, какие строки файла исправить. | Роль: учебный отдел |
| Требование | Система проверяет строки при загрузке: время, рабочий день по сетке пар, ссылки, группы занятия; если есть хотя бы одна ошибка, файл не загружается целиком; выводится список ошибок. Сетка пар настраивается; позже — совпадение занятия с парой и несколько сеток. | Т-13–Т-20, Т-65 · Must; Т-67, Т-68 · Could |
| Критерий | Файл с ошибками не загружен, черновик не изменился; по каждой ошибке видны номер строки и причина. | Проверка: тест на файле с ошибками |
| **Ц5. Группы занятий и потоки** |  |  |
| Инсайт | В схеме кейса у занятия одна группа, а потоковое занятие идёт сразу у нескольких групп. Команда решила хранить группы занятия в отдельной таблице lesson_groups. | Источник: кейс, разд. «Данные»; решение команды (ERD) |
| Потребность | Учебному отделу нужно заносить потоковое занятие один раз для всех его групп. | Роль: учебный отдел |
| Требование | Группы занятия всегда хранятся в lesson_groups: у обычного занятия одна строка, у потокового — несколько. | Т-21 · Must |
| Критерий | Поток на 3 группы — одна запись в lessons и 3 строки в lesson_groups. | Проверка: просмотр базы |
| **Ц6. Поиск конфликтов** |  |  |
| Инсайт | Конфликт фиксируется, если интервалы занятий пересекаются по времени на одну дату по аудитории, преподавателю или группе. Критерий приёмки 1 — выявлять конфликты по аудитории, группе и преподавателю. | Источник: кейс, разд. 2 п. 2, критерии приёмки п. 1 |
| Потребность | Учебному отделу нужно находить все пересечения в расписании, чтобы их исправить. | Роль: учебный отдел |
| Требование | Явное правило пересечения (занятия встык не пересекаются); поиск конфликтов типов 1–3 (аудитория, преподаватель, группа) с учётом потоков; тип 4 — вместимость по сумме групп занятия. | Т-22–Т-25, Т-66 · Must; Т-26 · Should |
| Критерий | На тестовом наборе пересечения по аудитории, преподавателю и группе находятся; занятия встык конфликта не дают; поток сам с собой конфликта не даёт; превышение вместимости — конфликт типа 4. | Проверка: тест на тестовом наборе |
| **Ц7. Обработка конфликтов** |  |  |
| Инсайт | Алгоритм выявляет конфликты и сохраняет их в отчёт с указанием type, date, time_range, participants; один конфликт может включать несколько занятий. Команда определяет приоритеты устранения конфликтов (например, аудитория выше, чем преподаватель). | Источник: кейс, разд. 2 п. 3, разд. 8 |
| Потребность | Учебному отделу нужно видеть каждую накладку со всеми её занятиями и получать актуальный результат после исправлений. | Роль: учебный отдел |
| Требование | Конфликт сохраняется с type, date, time_range, participants и списком lessons[]; проверка запускается кнопкой; повторная проверка пересчитывает всё заново; конфликты упорядочены по приоритету устранения. | Т-27–Т-30 · Must; Т-31 · Should |
| Критерий | У каждого конфликта заполнены все поля и все lesson_id; после исправления и повторной проверки исправленного конфликта нет. | Проверка: тест на тестовом наборе |
| **Ц8. Отчёт «Конфликты расписания»** |  |  |
| Инсайт | Отчёт содержит тип, дату и диапазон времени, идентификаторы участников и список lesson_id; показывает количество и типы конфликтов, детализацию по датам и преподавателям; есть сводные показатели и фильтры. Критерий приёмки 2 — отображать детали. | Источник: кейс, разд. 2 п. 3, разд. 4, критерии приёмки п. 2 |
| Потребность | Учебному отделу и администратору нужно видеть, какие конфликты есть, сколько их и каких типов, и находить нужные. | Роль: учебный отдел, администратор расписания |
| Требование | Отчёт «Конфликты расписания» с полями, детализацией по датам и преподавателям, сводными показателями (всего, по типам, доля расписаний без конфликтов) и фильтрами. | Т-32–Т-36 · Must |
| Критерий | Все поля заполнены; сумма по типам равна общему количеству; доля совпадает с ручным подсчётом; фильтры оставляют только подходящие конфликты. | Проверка: тест на тестовом наборе, сверка с ручным расчётом |
| **Ц9. Экспорт CSV** |  |  |
| Инсайт | Критерий приёмки 3 — экспорт отчёта в CSV: type, date, time_range, room/teacher/group, lessons[]. | Источник: кейс, разд. 4, критерии приёмки п. 3 |
| Потребность | Учебному отделу нужно выгрузить отчёт о конфликтах в файл. | Роль: учебный отдел |
| Требование | Экспорт отчёта в CSV: type, date, time_range, participants, lessons[]. | Т-37 · Must |
| Критерий | В файле все колонки, строк столько же, сколько конфликтов в отчёте. | Проверка: тест на тестовом наборе |
| **Ц10. Метрики качества расписания** |  |  |
| Инсайт | Команда добавляет метрики качества расписания: конфликтность, плотность, стабильность. | Источник: кейс, разд. 8 |
| Потребность | Нужно оценивать качество расписания в цифрах. | Роль: администратор расписания |
| Требование | Метрики конфликтности, плотности и стабильности. | Т-38 · Should |
| Критерий | Значения совпадают с ручным расчётом. | Проверка: сверка с ручным расчётом |
| **Ц11. Согласование и публикация** |  |  |
| Инсайт | Цель кейса — сократить время согласования расписания. Администратор расписания отвечает за контроль исправлений и пересогласование. KPI кейса — число конфликтов не больше порога, а не ноль, поэтому расписание с конфликтами можно отправить, но с объяснением. | Источник: кейс, бизнес-цель, KPI, разд. 2 п. 5; решение команды |
| Потребность | Учебному отделу нужно передать исправленное расписание на утверждение, администратору — опубликовать его или вернуть на доработку с объяснением. | Роль: учебный отдел, администратор расписания |
| Требование | Статусы: Черновик → На согласовании → Опубликовано, при отказе — обратно в Черновик; учебный отдел отправляет расписание на согласование, при конфликтах — с обязательным комментарием; администратор публикует или отклоняет с комментарием; на согласовании черновик не правится; черновик один; публикация заменяет предыдущую. | Т-39, Т-40, Т-62, Т-63 · Must |
| Критерий | Отправленное расписание появляется у администратора и не правится; после публикации оно опубликовано и заменило предыдущее; после отказа оно снова черновик с комментарием администратора. | Проверка: вход под ролью |
| **Ц12. Интерфейс** |  |  |
| Инсайт | Ожидаемый артефакт кейса — UI-прототип просмотра расписания и конфликтов. | Источник: кейс, «Ожидаемые артефакты» |
| Потребность | Каждой роли нужно видеть на экране то, с чем она работает. | Роль: все роли |
| Требование | Экран для каждой роли: публичный просмотр опубликованного расписания с фильтрами; черновик расписания и уведомления о конфликтах у учебного отдела; расписания на публикацию у администратора; потоки помечены. | Т-41, Т-42 · Must; Т-43, Т-44 · Should |
| Критерий | Под каждой ролью открывается её экран, без входа — публичный просмотр; поток виден в расписании каждой своей группы с пометкой. | Проверка: вход под ролью, открытие без входа |
| **Ц13. Скорость** |  |  |
| Инсайт | Алгоритм должен обрабатывать от 150 занятий интерактивно — быстрее 3 секунд. | Источник: кейс, разд. 3 (Производительность) |
| Потребность | Учебному отделу нужно получать результат проверки без долгого ожидания. | Роль: учебный отдел |
| Требование | Проверка 150+ занятий быстрее 3 секунд с замером в журнале; желательно запас на 1500 занятий; отчёт и фильтры — до 3 секунд. | Т-45 · Must; Т-46, Т-47 · Could |
| Критерий | Длительность проверки на основном тестовом наборе в журнале меньше 3 секунд. | Проверка: замер по журналу |
| **Ц14. Надёжность** |  |  |
| Инсайт | Повторный импорт CSV не создаёт дубликаты записей. | Источник: кейс, разд. 3 (Надёжность) |
| Потребность | Учебному отделу нужно доверять данным и результатам проверки. | Роль: учебный отдел |
| Требование | Повторная загрузка не создаёт дублей; проверка не меняет расписание; повторный запуск даёт тот же результат. | Т-11 · Must; Т-48, Т-49 · Should |
| Критерий | Данные до и после проверки совпадают; два запуска подряд дают одинаковый список конфликтов. | Проверка: тест на тестовом наборе |
| **Ц15. Журнал проверок (трассируемость)** |  |  |
| Инсайт | Нужно фиксировать дату и время запуска проверки и количество найденных конфликтов. | Источник: кейс, разд. 3 (Трассируемость) |
| Потребность | Учебному отделу и администратору нужно видеть, что после исправлений конфликтов стало меньше. | Роль: учебный отдел, администратор расписания |
| Требование | Журнал проверок: каждый запуск с датой, автором, числом занятий и конфликтов, длительностью; записи не меняются; журнал видят учебный отдел и администратор; видна динамика конфликтов. | Т-50 · Must; Т-52, Т-53 · Should; Т-51 · Could |
| Критерий | После 3 запусков в журнале 3 полные записи; после исправления в новой записи конфликтов меньше. | Проверка: тест на тестовом наборе |
| **Ц16. Тестовые данные** |  |  |
| Инсайт | Данные — синтетика, объём — от 150 занятий. | Источник: кейс, разд. «Данные» |
| Потребность | Команде нужно проверить и показать работу системы на тестовых данных. | Роль: команда |
| Требование | Синтетические данные, минимум 150 занятий, включая потоковые занятия с разными случаями. | Т-54 · Must; Т-55 · Should |
| Критерий | В наборе не меньше 150 занятий и все три случая с потоками. | Проверка: просмотр базы |
| **Ц17. Платформа** |  |  |
| Инсайт | Технология кейса — 1С:Предприятие. Команда решила держать данные и логику в 1С. | Источник: кейс, «Используемые технологии»; решение команды |
| Потребность | Решение должно быть сделано на технологии кейса. | Роль: заказчик кейса |
| Требование | Данные и логика — в 1С:Предприятие 8.3; публичный просмотр — на сайте через бэкенд. | Т-56 · Must |
| Критерий | Импорт, проверка корректности, поиск конфликтов и отчёты работают в базе 1С. | Проверка: просмотр базы |
| **Ц18. Сайт** |  |  |
| Инсайт | Ожидаемый артефакт кейса — UI-прототип просмотра расписания. Команда решила: публичный просмотр — на сайте; сайт работает через API бэкенда, данные и логика остаются в 1С; вход на сайт — во вторую очередь. | Источник: кейс, «Ожидаемые артефакты»; решение команды |
| Потребность | Преподавателям, студентам и всем остальным нужно смотреть актуальное расписание в браузере, без установки 1С; учебному отделу и администратору — работать с сайта. | Роль: публичный просмотр, учебный отдел, администратор расписания |
| Требование | Публичный просмотр на сайте; после публикации в 1С расписание появляется на сайте; сайт получает данные только через API бэкенда; вход на сайт по учётным записям из 1С; кабинеты учебного отдела и администратора на сайте. | Т-57–Т-59 · Must; Т-60, Т-61 · Should |
| Критерий | Без входа сайт показывает опубликованное расписание; после публикации на сайте видно новое расписание; сайт не обращается к 1С напрямую; учебный отдел и администратор входят на сайт под учётными записями из 1С. | Проверка: открытие сайта, публикация, вход под ролью |

## 2. Требования по MoSCoW

### Must (47)

| ID | Требование | Критерий проверки | Цепочка |
|---|---|---|---|
| Т-01 | Учебный отдел: загрузка CSV (создаёт или заменяет черновик, Т-64), запуск проверки конфликтов, просмотр отчёта и уведомлений о конфликтах, экспорт CSV. | Под пользователем учебного отдела доступны все перечисленные действия. | Ц1 |
| Т-02 | Администратор расписания: просмотр расписания и отчётов, подтверждение публикации, создание учётных записей и назначение ролей; загружать и править расписание не может. | Под администратором доступны все перечисленные действия; загрузка и правка недоступны. | Ц1 |
