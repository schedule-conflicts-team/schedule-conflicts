# План разработки MVP

Кейс 11 "Учебное расписание и конфликтология". Проект плана от 17.11.2026.

## 1. Срок и условия

В плане от 17.11 MVP нужен к **22 декабря 2026 года**. Плановое завершение - 21 декабря; один день остаётся в запасе.

Исходный расчёт включает 42 задачу на 155 человеко-час. В исходном расчёте вся работа считается предстоящей: готовые части пока не проверены. Для сравнения взяты прежние оценки из [пакетов работ](work-packages.md). Женя отвечает за итог всех пакетов; роли участников описаны в [RACI](raci.md).

Исходный график предусматривает четыре итерации по 8-9 дней с пределом 16 часов на человека в каждой. Женя выделяет в среднем около 10 часов в неделю на задачи; время на координацию и ревью - отдельно. Нагрузка распределена неравномерно: в первых трёх итерациях у Жени по 16 часов, то есть около 12-13 часов в неделю, в последней - 3 часа.

Проверки отдельных компонентов относятся к их задачам, общая проверка системы - к WP-05. Координация, отдельное ревью и исправления сверх оценок требуют дополнительного времени.

## 2. Задачи и зависимости

Код задачи используется для ссылок внутри плана. В колонке Issue позже появится ссылка на задачу GitHub. WP - код пакета работ.

"Предшественники" - задачи, которые должны быть готовы до начала работы. В расчёте принят такой порядок; на практике часть работ можно начать раньше на тестовых данных. Один человек выполняет свои задачи по очереди.

Запись "1: 3 ч; 2: 1 ч" означает три часа в первой итерации и один час во второй. В колонке "Чел.-ч" учтены дополнения по Docker, а распределение часов по итерациям сохранено по плану от 17.11.

## 4. Порядок и критический путь

Ниже приведён расчёт от 17.11 без дополнений по развёртыванию.

Сначала Женя готовит модель 1С и контракты обмена. Затем параллельно идут работы Ани и Даши в 1С, разработка API и базы у Жени, сайт у Вовы. Алиса готовит сценарии и связывает их с Must-требованиями. После сборки компонентов - запуск на сервере, проверка всей системы и приёмка.

Если учитывать только зависимости задач, критический путь занимает 48 часов:

`1C-01 -> 1C-03 -> 1C-04 -> 1C-06 -> 1C-11 -> 1C-12 -> 1C-15 -> 1C-16 -> 1C-17 -> 1C-18 -> SYS-03 -> SYS-04 -> SYS-05 -> SYS-06`

Но Женя делает сразу несколько частей системы. С учётом очереди его работ срок определяет более длинная цепочка - 61 час:

`1C-01 -> API-01 -> API-02 -> DB-01 -> 1C-02 -> API-03 -> DB-02 -> DB-04 -> API-05 -> DB-03 -> 1C-16 -> API-04 -> 1C-18 -> SYS-03 -> SYS-04 -> SYS-05 -> SYS-06`

В обеих цепочках SYS-05 занимает 3 часа Вовы; час замера Жени проходит параллельно. Вторая цепочка включает как зависимости, так и очередь работ одного человека. Например, прототип календаря идёт после схемы PostgreSQL, потому что обе задачи делает Женя.

Эта цепочка распределена на четыре итерации. Задержки могут сдвинуть срок, если их не удастся покрыть запасом времени или изменением порядка работ. Конкретные дни работы внутри итерации согласуются с исполнителями.

## 7. Контроль и связанные материалы

В конце каждой итерации команда проверяет результат, обновляет Issues и оценки оставшейся работы. При задержках Женя пересматривает план.

Для сдачи практики 6 вместе с планом нужны:

- задачи в GitHub с исполнителями, оценками, зависимостями и критериями готовности;
- таблица "Must-требование -> пакет -> задачи -> проверка" и приёмочные сценарии;
- проверенные статусы поручений, обновлённые риски и изменения;
- C4 Component; связь компонентов с задачами приведена в разделе 2.

Ссылки на недостающие материалы добавляются по мере подготовки.
