# Модель хранения данных 1С

Дата: 23.11.2026. Статус: **примерная рабочая версия**. Модель уточняется по ходу
реализации: исполнители вправе пересматривать решения, внося изменения в этот документ;
отдельный ADR для таких уточнений не требуется.

Основание: [архитектура 1С](1c.md) (разделы 4, 7, 8, 10–12), задача #62 (1C-01).
Схема PostgreSQL и контракты обмена описаны отдельно: задачи DB-01 и API-01.

## 1. Общие соглашения

Идентификаторы запусков проверок, конфликтов и публикаций: UUID, строка(36). UUID
генерируется там, где создаётся объект, поэтому общий счётчик под блокировкой не нужен.
В отчётах конфликт опознаётся по типу, ресурсу и интервалу; ID технический, он же
используется в CSV-экспорте.

Коды справочников: строка(9), уникальные, с автонумерацией для ручного создания.
При импорте CSV коды задаются файлом.

Время занятий хранится раздельно: `Дата` содержит только дату, `Начало` и `Окончание`
содержат только время с пустой датой. Для сравнения интервалов дата и время объединяются.

Пользователи: штатные пользователи информационной базы. Автор, инициатор проверки
и администратор решения хранятся как имя пользователя, строка(100). Отдельный справочник
пользователей не создаётся.

Проверки состояний, прав и ограничений живут на сервере в общих модулях и срабатывают
в том числе при вызове в обход форм. Формы вызывают серверные операции, а не пишут данные сами.

Неизменяемые данные (снимки, содержимое публикации) защищают код и права: интерактивный
доступ к ним не выдаётся, записывает только серверная операция создания. Платформенного
«замка на запись» у реквизитов и регистров нет.

## 5. Снимок согласования

### Хранение

Снимок хранится в реквизите `Снимок` документа «Расписание», тип `ХранилищеЗначения`.
В любой момент у расписания нужен максимум один актуальный снимок: при передаче он
создаётся, при отказе заменяется новым, при одобрении фиксируется навсегда. Хранение
отказных снимков не требуется, поэтому отдельный регистр или табличная часть документа
для снимков не нужны.

Содержимое снимка непрозрачно для запросов: календарь и отчёт читают его целиком
и фильтруют в памяти. На объёме MVP (150+ занятий) это приемлемо.

### Состав снимка

Снимок копирует сами значения, а не только ссылки: изменение справочника не должно менять
снимок. Структура в `ХранилищеЗначения`:

| Поле | Тип | Содержимое |
|---|---|---|
| ВремяФиксации | Дата (дата и время) | Момент создания снимка |
| Занятия | Таблица значений | Занятия со скопированными значениями, состав ниже |
| СправочныеДанные | Таблица значений | Использованные справочные записи со скопированными значениями |
| СеткаПар | Таблица значений | Пары: номер, начало, окончание |

Колонки таблицы `Занятия`:

| Колонка | Тип | Содержимое |
|---|---|---|
| Дата | Дата (только дата) | Дата занятия |
| Начало | Дата (только время) | Время начала |
| Окончание | Дата (только время) | Время окончания |
| КодДисциплины | Строка | Внешний код дисциплины |
| НазваниеДисциплины | Строка | Скопированное название |
| КодПреподавателя | Строка | Внешний код преподавателя |
| ФИОПреподавателя | Строка | Скопированное ФИО |
| КодАудитории | Строка | Внешний код аудитории |

| Вместимость | Число | Вместимость аудитории на момент фиксации |
| Группы | Массив структур | Код, название и численность каждой группы |

Колонки таблицы `СправочныеДанные`:

| Колонка | Тип | Содержимое |
|---|---|---|
| ВидСправочника | Строка | Группы, Аудитории, Преподаватели или Дисциплины |
| Запись | СправочникСсылка | Ссылка для повторного чтения текущих значений при одобрении |
| Код | Строка | Внешний код записи |
| Название | Строка | Скопированное название |
| Численность | Число | Для групп |
| Вместимость | Число | Для аудиторий |

Ссылки в `СправочныеДанные` нужны только для сравнения при одобрении; отображение
и публикация используют скопированные значения. Сетка пар фиксируется, потому что влияет
на проверку границ рабочего дня.

### Жизненный цикл и защита

При передаче на согласование серверная операция собирает структуру из текущих данных
и записывает в реквизит `Снимок` вместе со сменой состояния, в одной транзакции. Отказ
возвращает документ в «Черновик»; снимок остаётся до следующей передачи, которая заменяет
его новым. Одобрение навсегда фиксирует снимок: в состоянии «Согласовано» запись реквизита
запрещена серверной проверкой.

Реквизит не выводится в редактируемые поля форм, поэтому интерактивная запись невозможна.
Пишет только серверная операция передачи.

### Чтение

Календарь и отчёт в состояниях «НаСогласовании» и «Согласовано» читают `Снимок.Получить()`
и строят отображение из таблиц значений снимка. В «Черновике» они читают живые занятия.
Код преобразования общий. Публикация готовится из одобренного снимка (раздел 7).

### Блокировка одобрения при изменении справочников

При одобрении сервер заново читает использованные справочные записи (по ссылкам
из `СправочныеДанные`) и текущую сетку пар, затем сравнивает их значения с копиями
в снимке. Любое расхождение использованных данных запрещает одобрение с показом причины
и требует возврата на доработку. Изменения записей, не использованных в расписании,
одобрению не мешают.

Сравнение охватывает все скопированные значения, включая названия. Поэтому даже
исправление названия в использованной записи требует повторной передачи расписания.

## 6. Регистры проверок

Проверка идёт синхронным серверным вызовом: кнопка запускает серверную операцию, она
считает конфликты и сохраняет результат, форма показывает итог. Фоновые задания
не используются, клиент ожидает завершения. Ориентир производительности: менее 3 секунд
на 150+ занятий (Т-45, замер от нажатия кнопки до сохранённого результата).

Регистров три, все независимые непериодические. У регистров сведений нет табличных частей,
а число участников конфликта переменно: три занятия с одинаковым временем в одной
аудитории дают один конфликт с тремя участниками. Поэтому связь конфликт–занятие вынесена
в отдельный регистр. Это даёт переходы «конфликт → занятия» и «занятие → конфликты»
и фильтр по группе (Т-36) обычными запросами.

### Запуск и защита от второго одновременного запуска

Старт проверки: отдельная короткая транзакция. Сначала набор записей `ИсторияПроверок`
по расписанию блокируется исключительно, затем ищется запись «Выполняется». Если она есть
и сеанс с записанным номером жив (`ПолучитьСеансыИнформационнойБазы`), запуск получает
понятный отказ «проверка уже выполняется»; так защита работает и для запуска из другой
сессии. Если сеанс мёртв, зависшая запись удаляется и запуск продолжается. Дополнительно
запись «Выполняется» старше 5 минут считается зависшей независимо от сеанса: это страховка
от случаев, которые проверка живости не покрывает. Затем создаётся запись «Выполняется»
с ID запуска, номером текущего сеанса, инициатором и временем старта; после коммита она
видна всем сессиям.

Алгоритм читает занятия и справочные данные и считает конфликты. Весь код выполнения
обёрнут в `Попытка…Исключение`: при любом исходе запись «Выполняется» закрывается,
«Завершён» с итогами или «Ошибка», поэтому флаг не может зависнуть. Завершение: одна
транзакция удаляет старые детали расписания, записывает новые конфликты и участников,
дополняет запись истории итогами и длительностью. Перед сохранением алгоритм сравнивает
входные данные с теми, что читал на старте. Если данные изменились во время проверки,
например правкой из другой сессии, результат сохраняется сразу устаревшим
(«Актуально» = Ложь), а пользователю предлагается повторить проверку.

### Устаревание результатов

Результаты гасятся при записи данных. Любая запись занятий расписания (ручная правка,
удаление, импорт) гасит признак «Актуально» у его последней проверки; это делает общая
операция сохранения занятий. Изменение справочной записи гасит последние проверки тех
расписаний, которые её используют; список расписаний даёт запрос через занятия, код живёт
в общей операции записи справочников. Изменение сетки пар гасит последние проверки всех
расписаний, потому что сетка общая.

Отчёт и календарь показывают признак актуальности из записи истории. Повторная проверка
создаёт новый запуск и новые детали.

## 7. Регистр публикаций

Независимый непериодический регистр сведений `Публикации`.

Измерение:

| Измерение | Тип | Назначение |
|---|---|---|
| IDПубликации | Строка(36), UUID | Постоянный идентификатор публикации |

Ресурсы:

| Ресурс | Тип | Назначение |
|---|---|---|
| Номер | Число(10,0) | Возрастающий номер публикации |
| Расписание | ДокументСсылка.Расписание | Согласованное расписание |
| СнимокОтправки | ХранилищеЗначения | Неизменный снимок отправки |
| СостояниеДоставки | ПеречислениеСсылка.СостоянияДоставкиПубликации | Ожидает / Ошибка / Доставлено |
| ВремяСоздания | Дата (дата и время) | Подготовка публикации |
| ВремяПоследнейПопытки | Дата (дата и время) | Последняя попытка доставки |
| ТекстОшибки | Строка(1000) | Ошибка последней попытки |
| ВремяУспешнойДоставки | Дата (дата и время) | Успешная доставка |

Номер назначается при подготовке: максимум по регистру + 1 под блокировкой набора записей
регистра в транзакции одобрения.

Снимок отправки собирается из одобренного снимка согласования и сохраняется один раз.
Повторная отправка использует те же ID, номер и содержимое; обновляются только поля
доставки. Состав снимка в формате обмена определит контракт API-01; до его утверждения
снимок хранит структуру, аналогичную снимку согласования.

Одобрение и подготовка публикации сохраняются вместе (раздел 8). Отправка начинается
после фиксации транзакции. Сбой доставки не отменяет согласование и не мешает следующему
черновику.

Запись регистра создаёт только серверная операция подготовки, интерактивный доступ
не выдаётся. Поля доставки обновляет только серверный код отправки.

## 8. Транзакции и блокировки

Режим блокировок управляемый. Блокировки короткие; длительные операции, например
HTTP-отправка, идут вне транзакций.

| Операция | Границы транзакции | Блокировки |
|---|---|---|
| Создание черновика (в т.ч. копированием) | Проверка единственности + создание документа + создание новых занятий при копировании | Исключительная блокировка всего множества Документ.Расписание |
| Ручное изменение / удаление занятия | Валидация + запись + маркирование устаревания | Исключительная блокировка объекта документа расписания |
| Импорт занятий | Валидация всего файла до транзакции; в транзакции: удаление старых занятий + запись новых + маркирование устаревания | Блокировка объекта документа расписания |
| Импорт справочников | Применение всего подтверждённого набора + маркирование устаревания затронутых расписаний | Блокировки изменяемых элементов справочников |
| Старт проверки | Создание записи «Выполняется» | Блокировка набора записей ИсторияПроверок по расписанию |
| Финиш проверки | Удаление старых деталей + запись новых + итоги истории | Блокировка наборов записей деталей по расписанию + запись истории |
| Передача на согласование | Валидация и проверка выполняются до неё; в транзакции: запись снимка + смена состояния | Блокировка объекта документа |
| Отказ администратора | Смена состояния + причина | Блокировка объекта документа |
| Одобрение | Сравнение значений со снимком + решение + состояние «Согласовано» + запись публикации (номер max+1, снимок отправки) | Блокировка объекта документа + блокировка набора записей Публикации |
| Отправка / повтор | Обновление полей доставки | Блокировка записи публикации |

### Единственный рабочий документ

Одновременно может существовать только один рабочий документ: «Черновик» или
«НаСогласовании». Простой проверки «есть ли черновик» недостаточно: два пользователя,
одновременно нажавшие «Создать», могут оба увидеть отсутствие черновика и создать два
документа. Поэтому создание блокирует всё множество документов «Расписание» исключительно.
Документа ещё нет, блокировать поштучно нечего, а блокировка всего множества сериализует
и создание: второе создание ждёт завершения первого и видит уже созданный документ.
Под блокировкой выполняется запрос документов в состояниях «Черновик» / «НаСогласовании»;
если такой документ есть, следует понятный отказ. Блокировка держится миллисекунды,
на объёме MVP ожидание незаметно.

### Атомарность наборов

Один применяемый набор импорта пишется в одной транзакции; при ошибке платформа откатывает
его целиком, частично изменённой базы не остаётся.

## 9. Серверные правила и доступ

Роли: УО редактирует черновик и справочники, запускает проверки, передаёт расписание
на согласование. Администратор расписания просматривает снимок и принимает решение,
занятия не редактирует. Интерактивные права на регистры проверок, публикаций и реквизит
снимка не выдаются.

Используемые в занятиях справочные записи удалять нельзя: серверная проверка срабатывает
при пометке удаления и физическом удалении. Неиспользуемые записи удалять можно.

Пустой черновик допустим; передача пустого расписания запрещена.
