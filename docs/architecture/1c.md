# Архитектура подсистемы 1С

Дата: 13.11.2026. Статус: черновик для обсуждения и проверки командой.

Документ описывает планируемое устройство 1С для MVP: работу пользователей, данные и компоненты. Готовность функций здесь не отражается.

## 1. Назначение и границы

1С хранит рабочее расписание и отвечает за его подготовку, проверки, согласование и отчёты. УО и администратор работают в 1С. Бэкенд хранит последнюю успешно опубликованную копию и предоставляет API публичному сайту. Сайт не обращается к 1С напрямую и остаётся доступным при её отключении.

| Участник | Действия |
|---|---|
| Учебный отдел (УО) | Готовит справочники и занятия, разбирает конфликты, передаёт расписание на согласование |
| Администратор расписания | Согласовывает или отклоняет расписание с причиной; занятия не редактирует |
| Посетитель сайта | Без входа просматривает расписание с фильтрами по группе, преподавателю и аудитории |

В MVP входят календарь, ручное добавление, изменение и удаление занятий, импорт CSV, проверки пересечений и вместимости, согласование, публикация, отчёт и экспорт. Автоматическое составление расписания, перетаскивание занятий и рабочие кабинеты на сайте не входят.

## 2. Работа с расписанием

Основной путь: подготовка черновика -> проверка и исправление конфликтов -> согласование -> публикация.

Черновик можно создать пустым, заполнить из CSV или получить копированием согласованного расписания. При копировании создаются новые занятия; исходное расписание не меняется.

| Состояние | Что разрешено | Переход |
|---|---|---|
| Черновик | Редактирование, импорт и проверки | Передача на согласование |
| На согласовании | Просмотр снимка и решение администратора; занятия менять нельзя | Одобрение -> Согласовано; отказ с причиной -> тот же Черновик |
| Согласовано | Просмотр и повторная отправка публикации | Исправления - только через новый черновик |

Одновременно может быть только один рабочий документ: "Черновик" или "На согласовании". После согласования разрешён следующий черновик, даже если предыдущая публикация ещё не доставлена.

## 3. Интерфейс

Основной экран - недельный календарь: дни по колонкам, время по вертикали, границы пар отмечены. Пересекающиеся занятия видны одновременно. Пользователь выбирает неделю и фильтры по группе, преподавателю и аудитории.

Нажатие на занятие открывает форму редактирования его данных. Из списка конфликтов можно перейти к связанным занятиям в календаре. Положение карточек рассчитывается при отображении и не хранится в базе.

## 4. Объекты данных

Основные объекты хранения:

| Объект | Содержание и назначение |
|---|---|
| Документ "Расписание" | Название, состояние, автор и время создания, комментарий УО, сведения о решении администратора, причина отклонения, ссылка на исходное расписание при копировании |
| Справочник "Занятия" | Ссылка на расписание, дата, время начала и окончания, дисциплина, преподаватель, аудитория; группы - в табличной части |
| Справочник "Группы" | Код, название, численность |
| Справочник "Аудитории" | Код, название или номер, вместимость |
| Справочник "Преподаватели" | Код, ФИО |
| Справочник "Дисциплины" | Код, название |
| Справочник "Сетка пар" | Одна запись на пару: номер, время начала и окончания; общая сетка для MVP |
| Регистры проверок | История запусков и результаты поиска конфликтов (раздел 7) |
| Снимок согласования | Копия проверенных данных для рассмотрения и последующего просмотра (раздел 8) |
| Регистр публикаций | Идентификатор и возрастающий номер публикации, расписание, сохранённый снимок отправки, состояние доставки, последняя попытка и ошибка, время успешной доставки |

При смене состояния расписания занятия остаются на месте. Одно занятие может объединять несколько групп в поток.

Сетка пар задаёт ориентиры календаря и границы рабочего дня. Занятие не обязано начинаться и заканчиваться точно по сетке пар.

## 5. Компоненты и взаимодействие

Компонент - часть системы со своей задачей. В коде ему могут соответствовать несколько общих модулей и объектов метаданных 1С.

| Компонент | Ответственность |
|---|---|
| Управление расписанием | Создаёт и копирует черновик, сохраняет занятия, проверяет допустимость действий, меняет состояния, управляет согласованием, запускает проверки и публикацию |
| Импорт | Читает CSV и передаёт подготовленные занятия управлению расписанием. Загружает справочники после подтверждения изменений и отмечает связанные результаты проверок как устаревшие |
| Проверка данных расписания | Проверяет правильность данных при ручном вводе и импорте. Возвращает ошибки, но сама не сохраняет занятия |
| Поиск конфликтов | Ищет конфликты во всём расписании, сохраняет результаты и историю запусков. Занятия не меняет |
| Отчётность | Показывает сохранённые результаты проверок, позволяет отфильтровать и выгрузить их |
| Публикация | Готовит и сохраняет снимок согласованных данных, отправляет его бэкенду, позволяет повторить отправку и сохраняет её результат |

Формы и календарь вызывают управление расписанием, форма загрузки - импорт. Импорт проверяет подготовленные занятия через компонент проверки данных и передаёт их управлению расписанием для сохранения. Управление расписанием также использует общую проверку данных, запускает поиск конфликтов и при одобрении вызывает публикацию. Публикация обращается к бэкенду.

Календарь и отчётность читают одни сохранённые результаты проверок и не пересчитывают конфликты. Отдельного механизма маршрутов согласования нет.

## 6. Импорт и проверка данных

Для загрузки есть два отдельных действия: загрузка справочных данных и загрузка расписания. Предварительные файлы: `groups.csv`, `audiences.csv`, `teachers.csv`, `subjects.csv`, `time_slots.csv`, `lessons.csv`.

В CSV занятий разделитель колонок - `;`, несколько групп перечисляются через `|`. Связи со справочниками задаются кодами. Справочники не загружаются заново при каждом импорте занятий.

Изменения существующих справочных записей показываются одним списком. Пользователь выбирает, какие применить; остальные значения сохраняются. Снимки не переписываются.

Импорт занятий сначала проверяет весь файл. При ошибках показывает номера строк и причины, не изменяя черновик. Успешный импорт заменяет его занятия целиком. Один набор изменений применяется полностью или не применяется вовсе.

При ручном вводе и импорте действуют одинаковые проверки:

- все обязательные поля заполнены;
- занятие начинается раньше, чем заканчивается;
- указанные группы, преподаватель, аудитория и дисциплина существуют в справочниках;
- указана хотя бы одна группа, и группы в занятии не повторяются;
- занятие находится в пределах рабочего дня.

Если эти проверки нашли ошибки, данные сохранить нельзя. Конфликты между правильно заполненными занятиями не мешают сохранить черновик.

## 7. Поиск конфликтов и результаты

Проверяется всё расписание, независимо от выбранной недели и фильтров календаря. Система ищет занятия, которые идут одновременно в одной аудитории, у одного преподавателя или у одной группы. Также она проверяет, хватает ли мест в аудитории для всех групп занятия.

Занятия встык не конфликтуют. Занятие с несколькими группами не сравнивается само с собой.

Один конфликт пересечения относится к конкретной аудитории, преподавателю или группе и определённому промежутку времени. Пока набор пересекающихся занятий не меняется, это один конфликт. Когда к ним добавляется занятие или одно из них заканчивается, начинается новый интервал. Конфликты по разным аудиториям, преподавателям и группам учитываются отдельно.

Например, три занятия с одинаковым временем в одной аудитории образуют один конфликт с тремя участниками. Для занятий А 09:00-10:00, Б 09:30-10:30 и В 10:00-11:00 в одной аудитории получаются два конфликта: А/Б 09:30-10:00 и Б/В 10:00-10:30. Превышение вместимости - отдельный конфликт одного занятия.

Каждый запуск имеет собственный идентификатор. В истории сохраняются расписание, инициатор, время, количество занятий, число конфликтов всего и по типам, длительность. Успешная проверка без конфликтов тоже сохраняется.

Подробные конфликты с собственными идентификаторами и ссылками на занятия хранятся только для последнего запуска каждого расписания. От предыдущих запусков остаются итоговые показатели. Если данные, от которых зависит проверка, изменились, прежний результат отмечается как устаревший.

## 8. Согласование и снимки

Пустое расписание передать нельзя. Перед передачей система заново проверяет все данные и ищет конфликты по текущим справочникам. При конфликтах обязателен комментарий УО. Затем система сохраняет снимок проверенных данных и меняет состояние на "На согласовании".

Снимок хранит сами значения занятий и справочников, включая названия, численность групп и вместимость аудиторий. Ссылок недостаточно: изменение справочника не должно менять снимок.

Администратор видит данные снимка. Эти же данные показываются при просмотре ранее согласованного расписания. Если до одобрения изменились связанные с расписанием справочные данные и это влияет на проверки, система запрещает одобрение и объясняет причину. Расписание нужно вернуть на доработку и передать заново. Изменения записей, которые в этом расписании не используются, не мешают согласованию.

После отказа черновик работает с текущими справочниками. Повторная передача создаёт новый снимок.

## 9. Отчётность

Отчёт "Конфликты расписания" показывает итоговое количество конфликтов и распределение по типам, подробности и связанные занятия, детализацию по датам и преподавателям, время проверки и актуальность результатов. Предусмотрены фильтры и экспорт.

Метрика Т-35 показывает долю учебных дней без конфликтов. Каждый день считается отдельно для каждой группы: число таких дней без конфликтов делится на общее число дней с занятиями у всех групп. Если у занятия есть конфликт, день каждой участвующей в нём группы считается проблемным. Поток учитывается для каждой группы, но сам конфликт не дублируется. Дни без занятий исключаются; если занятий нет, выводится "Нет данных".

Метрики с приоритетом Should обсуждаются отдельно.

## 10. Публикация

При одобрении из согласованного снимка готовится публикация. Решение и подготовленная публикация сохраняются вместе; отправка начинается после сохранения. Результат доставки учитывается отдельно. Предварительные состояния: "Ожидает", "Ошибка", "Доставлено".

У каждой публикации есть постоянный идентификатор, возрастающий номер и неизменный снимок отправки. Повторная попытка использует те же идентификатор, номер и содержимое, а не собирает данные заново из текущих справочников.

Бэкенд принимает новую версию целиком и делает её доступной сайту только после успешного сохранения. Повтор уже принятой публикации не применяет её заново; более старая версия не заменяет новую. При ошибке прежняя опубликованная версия остаётся доступной.

Сбой доставки не отменяет согласование. До первой успешной публикации сайт показывает отсутствие опубликованного расписания отдельно от технической ошибки.

Передача выполняется по HTTPS со служебным ключом. Секрет не хранится в репозитории и не передаётся браузеру.

## 11. Требования к реализации

Права, состояния и ограничения проверяются на сервере, в том числе при вызове в обход форм. Все правила должны соблюдаться и при одновременной работе пользователей: нельзя создать второй рабочий документ, сохранить часть импорта или подменить проверенные данные при создании снимка.

Согласованные данные, снимок согласования и подготовленная публикация защищаются от перезаписи. Транзакции, блокировки и способы отслеживания изменений ещё нужно спроектировать.

## 12. Открытые вопросы

| Вопрос | Что нужно определить или проверить |
|---|---|
| Календарь и клиент | Прототип Планировщика: одновременные пересечения, поток, фильтры, отметки пар и открытие формы в выбранном клиенте |
| Хранение снимка | Проверить вариант с `ХранилищеЗначения`, чтение календарём и отчётом, защиту от перезаписи |
| Контракты CSV | Имена файлов, поля и типы, внешние коды, дубли по содержимому, правила применения комплекта справочников |
| Контракт публикации | Состав снимка, эндпоинты, идентификаторы, ответы на повтор и устаревшую версию, состояния доставки, обработка ошибок и настройка доступа |
| Операции компонентов | Параметры, результаты и ошибки общих серверных операций |
| Хранение и одновременная работа | Реквизиты и их типы, ключи регистров, версии, транзакции, блокировки и отслеживание изменений |
| Сверка требований | Согласовать расширение MVP с MoSCoW: редактирование, календарь, вместимость, импорт справочников и уточнённые состояния |
| Полнота Must | Уточнить вход и тестовые роли, правила дублей, показ количества загруженных занятий, полный замер времени, фильтры Т-36 и CSV-экспорт Т-37 |
| Производительность | Уточнить границы измерения и проверить ориентир: не менее 150 занятий, обработка менее 3 секунд |
| Существующая конфигурация | Сверить проектируемые объекты с текущим EDT-проектом перед реализацией |

В требованиях и roadmap нужно отдельно отразить расширение MVP и уточнённый процесс работы. Пока эти документы не обновлены, между ними и этим описанием могут быть расхождения.
