## Краткая последовательность работы

Ниже - общий порядок для всех участников. Действия через интерфейс EDT описаны
в разделе [«Работа через 1С:EDT»](#работа-через-1сedt). Правила задач, веток, коммитов
и запросов на слияние (Pull request, PR) остаются общими.

1. [Открыть назначенную задачу и изучить требования](#открыть-или-создать-задачу).
   При появлении новой работы можно самостоятельно создать задачу (Issue) и сообщить тимлиду.
2. [Создать ветку от актуального `main`](#обновить-main-и-создать-ветку).
3. [Выполнить задачу и сохранить изменения коммитами](#выполнить-задачу-и-создать-коммит).
4. [Перед PR обновить ветку относительно `main` и отправить её на GitHub](#обновить-и-отправить-ветку).
5. [Открыть PR по шаблону и дождаться ревью](#открыть-pr-и-дождаться-ревью).
6. [Если замечания есть, исправить их отдельными коммитами и отправить изменения](#исправить-замечания).
7. [После одобрения и закрытия обсуждений выполнить слияние PR](#влить-pr).
   Ветка на GitHub удалится автоматически, задача закроется через `Closes #N` в описании PR.
8. [Переключиться на `main` и обновить его](#обновить-локальный-main).

## Первоначальная настройка

Сначала выполнить [общую настройку](#общая-настройка). Для разработки 1С затем выполнить
[настройку 1С:EDT](#настройка-1сedt). Эти действия нужны при первом подключении проекта на компьютере.

### Общая настройка

Для работы через SSH ключ должен быть добавлен в аккаунт GitHub; для отправки изменений
также нужны права на репозиторий.

#### Клонирование репозитория

Открыть Git Bash в папке, где будет храниться проект, и создать локальную копию:

```bash
git clone git@github.com:schedule-conflicts-team/schedule-conflicts.git
```

После завершения клонирования перейти в папку проекта:

```bash
cd schedule-conflicts
```

Если репозиторий уже склонирован, повторно клонировать его не нужно: открыть терминал
в существующей папке проекта. Если SSH запрашивает парольную фразу ключа, ввести её.
При ошибке доступа, например `Permission denied (publickey)`, обратиться к тимлиду.

#### Имя и почта для коммитов

В папке проекта проверить, какие имя и почту использует Git:

```bash
git config user.name
git config user.email
```

Если значение не выведено или не подходит, выполнить соответствующую команду, заменив
текст в кавычках на имя или никнейм и адрес почты:

```bash
git config --local user.name "Имя Фамилия или никнейм"
git config --local user.email "адрес почты"
```

Флаг `--local` сохраняет настройки только для этого репозитория. Для проверки можно
повторить команды `git config user.name` и `git config user.email`.

Имя и почта попадают в коммиты и видны в публичном репозитории. Чтобы GitHub связывал
коммиты с аккаунтом, указать подтверждённую почту аккаунта или адрес GitHub `noreply`.
Адрес вида `ID+ник@users.noreply.github.com` можно найти в GitHub → Settings → Emails.

### Настройка 1С:EDT

Используются 1С:EDT **2026.1.3** и платформа 1С:Предприятие **8.3.27**.
Перед подключением установить их и выполнить общую настройку выше: локальная копия
репозитория уже должна существовать. Повторно клонировать её через EDT не нужно.

Исходники проекта EDT находятся в `1c/schedule-conflicts/`; имя проекта в EDT -
`schedule-conflicts-1c`. Рабочую область EDT и локальную информационную базу хранить
вне папки репозитория. Через Git передаются исходники конфигурации; содержимое локальной
информационной базы, например введённые преподаватели или аудитории, коллегам не передаётся.

#### Подключение репозитория и импорт проекта

1. Запустить EDT. Через **Окно → Показать панель → Другое…** открыть панели
   **Репозитории Git** и **Индексирование Git**.
2. В панели **Репозитории Git** выбрать добавление существующего локального репозитория.
   Указать корневую папку `schedule-conflicts`, в которой находится `.git`, выбрать
   найденный репозиторий и нажать **Добавить**. Указывать вложенную папку `1c/` не нужно.
3. Выбрать **Импортировать проекты из репозитория Git**, затем **Существующий локальный
   репозиторий** и добавленный репозиторий.
4. Выбрать **Импорт существующих проектов Eclipse**, затем найденный проект
   `schedule-conflicts-1c` из `1c/schedule-conflicts/` и завершить импорт.
5. Дождаться окончания обработки проекта. Проверить, что в дереве проекта видна конфигурация.

#### Создание локальной базы и первый запуск

1. Выделить проект и нажать кнопку запуска (зелёный значок). Выбрать **Тонкий клиент**, затем запуск
   приложения на файловой, клиент-серверной или удалённой информационной базе.
2. Выбрать создание новой информационной базы, затем **Создание информационной базы
   без конфигурации**. Указать понятное имя, например `schedule-conflicts-local`.
3. Выбрать установленную платформу **8.3.27** и локальную файловую базу. Если путь задаётся
   вручную, указать папку вне репозитория. Остальные параметры оставить по умолчанию;
   режим запуска - **Выбирать автоматически**.
4. Завершить создание и выбрать эту базу для запуска проекта. Включить
   **Запрашивать подтверждение при необходимости реструктуризации** и завершить настройку.
5. Дождаться обновления базы из проекта и запуска 1С:Предприятия. Проверить, что приложение
   открывается без ошибок.

Базу создать один раз; при следующих запусках использовать её же. Настройка повторяется
при подключении на другом компьютере или создании новой рабочей области EDT.

## Работа через терминал

В шаблонах команд значения в угловых скобках, такие как `<название-ветки>`,
нужно заменить данными задачи. Сами скобки `<` и `>` вводить не нужно.

Для работы через EDT использовать [отдельную последовательность](#работа-через-1сedt).
Ниже приведены команды для работы через терминал.

Предполагается, что Git настроен, доступ к GitHub есть, а репозиторий уже склонирован.
Открыть терминал в папке репозитория. Например, можно открыть папку проекта в VS Code
и выбрать Git Bash во встроенном терминале. Перед командами обратить внимание на текущую
папку и ветку; ветку можно проверить командой `git status`. Если команда завершилась
с ошибкой, не переходить к следующему шагу до выяснения причины.

### Открыть или создать задачу

Обычно задачи создаёт тимлид; он же назначает исполнителей. На GitHub открыть вкладку
**Issues**, найти назначенную задачу и прочитать её контекст, описание, критерии приёмки
и приложенные материалы. Если что-то непонятно, уточнить у тимлида.

Если обнаружена ошибка или появилась другая работа для проекта, любой участник может
создать задачу самостоятельно:

1. На вкладке **Issues** нажать **New issue**.
2. Указать название, контекст, что нужно сделать и критерии приёмки. Если нужны материалы,
   добавить ссылки на них.
3. Выбрать подходящие метки и тип задачи, если они доступны, и создать задачу. Сообщить
   тимлиду о новой задаче: исполнителя назначает он.

Так работа не потеряется: команда увидит, что нужно сделать, а описание и критерии
останутся в задаче. Через PR с ней можно будет связать выполненные изменения.

### Обновить `main` и создать ветку

Перед переключением проверить текущую ветку и состояние файлов:

```bash
git status
```

Если остались незакоммиченные изменения, сначала разобраться с ними; при необходимости
обратиться к тимлиду. Затем переключиться на локальный `main`:

```bash
git switch main
```

Получить последние изменения с GitHub:

```bash
git pull --ff-only
```

Эта команда обновит `main` без создания коммита слияния. Если она сообщает о расхождении
истории, остановиться и обратиться к тимлиду.

Создать ветку для задачи. Шаблон:

```bash
git switch -c <название-ветки>
```

После команды проверить, что в терминале указана новая ветка. Правила названий - в разделе
[«Ветки»](#ветки). Для каждой задачи нужна отдельная ветка.

### Выполнить задачу и создать коммит

Внести изменения в файлы проекта и проверить результат по критериям задачи. Для изменений 1С
также [проверить результат в локальной информационной базе](#выполнить-задачу-и-создать-коммит-1).

Посмотреть, какие файлы изменились:

```bash
git status
```

Добавить нужные файлы в индекс - набор изменений для следующего коммита. Шаблон:

```bash
git add <путь-к-файлу>
```

Если файлов несколько, указать их через пробел или добавить по отдельности. Путь с пробелами
заключить в кавычки. Повторить `git status` и проверить раздел **Changes to be committed**.
Затем посмотреть содержимое подготовленных изменений:

```bash
git diff --staged
```

Убедиться, что в коммит попадёт именно то, что нужно. Если просмотр открылся постранично,
нажать `q` для выхода.

Сохранить подготовленные изменения коммитом. Шаблон:

```bash
git commit -m "<тип>: <описание>"
```

Указать в сообщении тип и описание изменений. Формат и типы - в разделе
[«Коммиты»](#коммиты). При необходимости повторять подготовку файлов и создание коммитов по мере работы.

### Обновить и отправить ветку

Оставаясь в ветке задачи, получить актуальный `main` и, если нужно, перенести коммиты задачи
поверх него:

```bash
git pull --rebase origin main
```

Если возник конфликт, остановиться и обратиться к тимлиду. Если ветка уже была отправлена
на GitHub и после обновления не получается отправить изменения, тоже обратиться к тимлиду.

При первой отправке указать название ветки задачи. Шаблон:

```bash
git push -u origin <название-ветки>
```

Флаг `-u` связывает локальную ветку с веткой на GitHub. В дальнейшем обычные новые
коммиты в эту ветку можно отправлять командой `git push`.

### Открыть PR и дождаться ревью

На GitHub нажать **Compare & pull request** или открыть создание PR через вкладку
**Pull requests**. Заполнить заголовок и описание по шаблону: что сделано и как проверить.
В строке `Closes #<номер-задачи>` указать номер задачи.

Создать PR и проверить запрос ревьюера. Если ревьюер не назначен или долго не отвечает,
обратиться к тимлиду. Ревью проводит другой участник команды; подробнее - в разделе
[«Pull request»](#pull-request). Ревьюер проверяет изменения и сверяет их с критериями задачи.

### Исправить замечания

Если ревьюер оставил замечания, сначала разобрать их с тимлидом. Внести исправления в той же
ветке, проверить изменения и создать отдельный коммит. Шаблон команд:

```bash
git status
git add <путь-к-файлу>
git diff --staged
git commit -m "<тип>: <описание-исправления>"
git push
```

Указать пути изменённых файлов и сообщение коммита. После `git push` существующий PR
обновится - новый создавать не нужно. Ответить в обсуждении и попросить повторно проверить исправление;
обсуждение закрывает его инициатор. Если замечаний нет, этот шаг с исправлениями
пропускается.

### Влить PR

Слияние PR выполняет автор. После одобрения другим участником с правами Write и закрытия
всех обсуждений нажать **Merge pull request**, затем **Confirm merge**. Используется коммит слияния.
Проверить, что PR получил статус **Merged**, а связанная задача закрылась. Ветка на GitHub
удалится автоматически.

### Обновить локальный `main`

Вернуться в локальный `main` и получить изменения с GitHub:

```bash
git switch main
git pull --ff-only
```

Теперь локальный `main` готов для начала следующей задачи.

## Работа через 1С:EDT

Перед началом выполнить [настройку 1С:EDT](#настройка-1сedt).
Здесь описан тот же цикл задачи через интерфейс EDT. Создание задач, оформление PR,
ревью и слияние выполняются на GitHub по общим правилам.

В панели **Репозитории Git** действия выполнять для репозитория `schedule-conflicts`.
Текущая ветка отображается в квадратных скобках рядом с его именем. Если операция завершилась
с ошибкой, не переходить к следующему шагу до выяснения причины.

### Открыть или создать задачу

[Открыть или создать задачу на GitHub](#открыть-или-создать-задачу), изучить требования,
критерии приёмки и приложенные материалы. Запомнить номер задачи для названия ветки.

### Обновить `main` и создать ветку

1. Сохранить открытые файлы. В панели **Индексирование Git** проверить, что нет
   незакоммиченных изменений.
2. В контекстном меню репозитория выбрать **Переключить на → main**.
3. Открыть **Получить и слить…**. Выбрать **Remote** - `origin`, **Reference** - `main`,
   **При получении изменений** - **Перебазировать**. Нажать **Готово** и дождаться завершения операции.
4. В контекстном меню выбрать **Переключить на → Новая ветка…**. Создать ветку от актуального
   `main` по [общим правилам](#ветки), например `feat/12-add-teachers`.
5. Проверить, что рядом с именем репозитория отображается новая ветка.

Если остались незакоммиченные изменения, сначала разобраться с ними; при необходимости
обратиться к тимлиду. Для получения изменений использовать пункт **Получить и слить…**
с многоточием: он позволяет проверить параметры перед выполнением операции.

В локальном `main` собственные коммиты не создавать. При отсутствии таких коммитов обновление
с режимом **Перебазировать** просто продвигает `main` до полученной версии. В отличие от
`git pull --ff-only`, этот режим не запрещает перенос случайных локальных коммитов.
Если `main` содержит собственные коммиты, появились конфликты или неожиданные изменения,
остановиться и обратиться к тимлиду.

### Выполнить задачу и создать коммит

Перед параллельным изменением одного объекта метаданных согласовать работу с другим участником,
чтобы уменьшить вероятность конфликтов.

1. Внести изменения в проект EDT и сохранить файлы.
2. Запустить проект на своей локальной базе через настроенный **Тонкий клиент**. Дождаться
   обновления базы из проекта. Если EDT запрашивает подтверждение реструктуризации,
   проверить предлагаемые изменения перед подтверждением.
3. Проверить поведение по критериям задачи, включая обработку ошибочных данных,
   если она относится к задаче.
4. В панели **Индексирование Git** просмотреть неиндексированные изменения.
   Открыть изменённые файлы и проверить их содержимое.
5. Перенести нужные файлы в индекс. Проверить список индексированных файлов и их изменения.
6. Ввести сообщение по [правилам коммитов](#коммиты), например
   `feat: добавить справочник преподавателей`, и нажать **Фиксировать**.

Если появились неожиданные массовые изменения, сначала выяснить причину. Кнопку добавления
всех изменений в индекс (значок с двумя плюсами) использовать только после проверки всего списка.
Локальная база, рабочая область EDT, секреты и посторонние файлы в коммит попадать не должны.

Коммит сохраняется локально; отправка на GitHub выполняется отдельно. В одной ветке может быть
несколько коммитов. Для следующего законченного изменения повторить проверку, индексирование
и создание коммита. Создавать новый PR на каждый коммит не нужно.

После получения изменений из Git или переключения ветки дождаться обработки проекта в EDT,
затем обновить локальную базу из проекта перед проверкой. Содержимое базы не переключается
вместе с Git-веткой: после изменения структуры может потребоваться подготовить тестовые данные заново.

### Обновить и отправить ветку

Перед обновлением сохранить файлы и создать коммиты для подготовленных изменений.
Оставаясь в ветке задачи:

1. Открыть **Получить и слить…**. Выбрать **Remote** - `origin`, **Reference** - `main`,
   **При получении изменений** - **Перебазировать**. Нажать **Готово** и дождаться завершения операции.
2. Дождаться обработки обновлённого проекта в EDT и повторить проверку результата в локальной базе.
3. В контекстном меню репозитория выбрать **Отправить (Push) ветку…** с именем ветки задачи.
4. В диалоге проверить удалённый репозиторий `origin` и имя отправляемой ветки.
   Завершить отправку.

В поле **Reference** указать `main` как источник изменений; текущая ветка должна оставаться
веткой задачи. Это соответствует `git pull --rebase origin main` из раздела о работе через терминал.
Отправлять на GitHub нужно ветку задачи, а не `main`.

При конфликте остановиться и обратиться к тимлиду. Если ветка уже отправлялась и после rebase
обычная отправка не проходит, также обратиться к тимлиду; принудительную отправку самостоятельно
не выполнять.

### Открыть PR и дождаться ревью

На GitHub [открыть PR и запросить ревью](#открыть-pr-и-дождаться-ревью).
В разделе «Как проверить» указать шаги проверки в базе, необходимые тестовые данные и ожидаемый
результат. Данных из локальной базы автора у ревьюера нет: описать, как их подготовить.

### Исправить замечания

Если ревьюер оставил замечания, сначала разобрать их с тимлидом. Внести исправления в той же
ветке EDT, проверить их в базе, создать отдельные коммиты и отправить ветку.
Ответить в [обсуждении существующего PR](#исправить-замечания) и запросить повторную проверку.
Обсуждение закрывает его инициатор.

### Влить PR

После одобрения и закрытия обсуждений [выполнить слияние PR на GitHub](#влить-pr).
Слияние выполняет автор PR.

### Обновить локальный `main`

1. Сохранить открытые файлы и проверить, что нет незакоммиченных изменений.
2. В контекстном меню репозитория выбрать **Переключить на → main**.
3. Открыть **Получить и слить…**. Выбрать **Remote** - `origin`, **Reference** - `main`,
   **При получении изменений** - **Перебазировать**. Нажать **Готово** и дождаться завершения операции.
4. Дождаться обработки проекта в EDT. Перед следующим запуском обновить локальную базу из проекта.

Соблюдать [правило об отсутствии собственных коммитов в `main`](#обновить-main-и-создать-ветку-1).
Если остались незакоммиченные изменения, сначала разобраться с ними; при необходимости обратиться
к тимлиду. Теперь локальный `main` готов для начала следующей задачи.

## Справочник

### Типы веток и коммитов

Для веток и коммитов используется один набор типов. Тип ветки выбирают по задаче
в целом, а тип коммита - по конкретному изменению.

| Тип | Когда |
| ----- | ------- |
| `feat` | добавление функции, эндпоинта, экрана или скрипта |
| `fix` | исправление ошибки в коде, спецификации или данных |
| `docs` | изменение текста и документов |
| `refactor` | изменение структуры кода без изменения поведения |
| `test` | добавление или изменение тестов и контрольных примеров |
| `chore` | служебные изменения: настройки, зависимости, CI, наборы данных |

### Ветки

Формат: `тип/номер-задачи-описание`.

Правила:

- тип - один из [типов веток и коммитов](#типы-веток-и-коммитов);
- описание - латиницей, через дефис, 2-4 слова;
- одна ветка - одна задача.

Примеры:

```
feat/12-room-conflicts
fix/27-cancelled-lessons
docs/8-csv-format
```

### Коммиты

Формат: `тип: описание`.

Правила:

- тип - один из [типов веток и коммитов](#типы-веток-и-коммитов);
- описание - в инфинитиве: «добавить», «исправить», а не «добавил» или «добавлена»;
- описание - со строчной буквы, без точки в конце;
- вся первая строка - не длиннее ~72 символов;
- тело - только если из заголовка и изменений непонятно, **зачем** сделано изменение;
  указать причину, а не пересказ изменений;
- между заголовком и телом - пустая строка;
- каждый коммит ветки попадает в `main` и пишется по этим правилам;
- правки по ревью - отдельный коммит, тоже по этим правилам.

Примеры:

```
feat: добавить импорт расписания из CSV
fix: не учитывать отменённые занятия при поиске конфликтов
fix: учитывать пустые строки в CSV
docs: описать формат CSV для импорта
refactor: вынести проверку конфликтов в отдельный модуль
test: добавить контрольный пример с двойным бронированием аудитории
chore: добавить .editorconfig
```

Пример коммита с телом:

```
fix: не учитывать отменённые занятия при поиске конфликтов

Отменённое занятие оставалось в выборке и блокировало аудиторию:
УО не мог поставить замену в освободившийся слот.
```

### Pull request

Формат: заголовок `тип: описание` и описание по шаблону.

Правила:

- одна задача - один PR;
- заголовок - по [правилам коммитов](#коммиты), описывает весь PR целиком и попадёт в коммит слияния;
- описание - по шаблону, он подставляется сам;
- `Closes #N` - закроет задачу при слиянии;
- ревью - нужно одно одобрение другого участника с правами Write; ревьюер назначается автоматически;
- слияние - выполняет автор после одобрения и закрытия всех обсуждений.

Шаблон описания (`.github/pull_request_template.md`):

```markdown
Closes #

## Что сделано

-

## Как проверить

-
```

Пример:

```markdown
Closes #12

## Что сделано

- импорт расписания из CSV
- проверка формата: при ошибке - номер строки и причина

## Как проверить

Загрузить `data/cases/basic/input.csv` через «Импорт» - появятся 12 занятий.
Загрузить файл с пустой колонкой «Аудитория» - будет ошибка со строкой 3.
```
