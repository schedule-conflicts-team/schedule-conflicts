# Как работать с репозиторием

## Перед началом работы

Укажи имя и почту для коммитов:

```bash
git config --global user.name "Имя Фамилия / Никнейм"
git config --global user.email "почта"
```

Почта попадает в каждый коммит, и в публичном репозитории её видит кто угодно.
Если не хочешь её показывать, используй адрес вида `ID+ник@users.noreply.github.com`:
он есть в GitHub → Settings → Emails.

## Цикл работы

1. Взять задачу, назначить себя, перевести в «In progress».
2. Создать ветку от свежего `main`:

   ```bash
   git switch main && git pull
   git switch -c feat/12-room-conflicts
   ```

3. Работать и коммитить по правилам ниже.
4. Перед PR подтянуть `main` и запушить ветку:

   ```bash
   git fetch origin && git rebase origin/main
   git push -u origin feat/12-room-conflicts   # после rebase: git push --force-with-lease
   ```

5. Открыть PR по шаблону - ревьюер назначится сам.
6. Исправить замечания отдельными коммитами и запушить.
7. После approve, когда все обсуждения закрыты, нажать Merge.
   Ветка удалится сама, задача закроется через `Closes #N`.

## Ветки

Формат: `тип/номер-задачи-описание`

```
feat/12-room-conflicts
fix/27-cancelled-lessons
docs/8-csv-format
```

- тип - один из типов коммитов (см. ниже);
- описание - латиницей, через дефис, 2-4 слова;
- одна ветка - одна задача.

## Коммиты

Формат:

```
тип: описание

Тело - по необходимости.
```

| Тип | Когда |
| ----- | ------- |
| `feat` | появилось что-то новое: функция, эндпоинт, экран, скрипт |
| `fix` | было неправильно, стало правильно (в коде, спеке или данных) |
| `docs` | только текст и документы |
| `refactor` | код переделан, поведение то же |
| `test` | тесты и контрольные примеры |
| `chore` | всё остальное служебное: конфиги, зависимости, CI, датасеты |

Если сомневаешься, какой тип выбрать, - бери тот, что выше в таблице.

Описание:

- в инфинитиве: «добавить», «исправить», а не «добавил» или «добавлена»;
- со строчной буквы, без точки в конце;
- вся первая строка - не длиннее ~72 символов.

Тело пишется, только если из заголовка и диффа непонятно, **зачем** сделано изменение.
Пиши причину, а не пересказ диффа. Между заголовком и телом - пустая строка.

```
feat: добавить импорт расписания из CSV
fix: не учитывать отменённые занятия при поиске конфликтов
docs: описать формат CSV для импорта
refactor: вынести проверку конфликтов в отдельный модуль
test: добавить контрольный пример с двойным бронированием аудитории
chore: добавить .editorconfig
```

```
fix: не учитывать отменённые занятия при поиске конфликтов

Отменённое занятие оставалось в выборке и блокировало аудиторию:
УО не мог поставить замену в освободившийся слот.
```

Все коммиты ветки попадают в `main` как есть, поэтому каждый из них пишется по этим правилам.
Правки по ревью - отдельный коммит, тоже по правилам: `fix: учитывать пустые строки в CSV`.

## Обновление ветки

Если `main` ушёл вперёд, ветку обновляют через rebase - перед открытием PR
и когда нужно (конфликт или нужен чужой код из `main`):

```bash
git fetch origin
git rebase origin/main
# конфликт: поправить файлы, затем
git add <файлы>
git rebase --continue
# запутался - вернуть всё как было:
git rebase --abort

git push --force-with-lease
```

Без конфликтов то же самое делает кнопка в PR: стрелка рядом с «Update branch» → «Update with rebase».

- Rebase - только своей ветки: на ветке, где работает кто-то ещё, он перепишет чужую историю.
- Только `--force-with-lease`, не `--force`: он не затрёт чужие коммиты, если они появились в ветке.
- После rebase approve сбрасывается, поэтому лучше делать его до ревью.

## 1С

Разработка ведётся в 1С:EDT, исходники проекта лежат в `1c/`.
Процесс общий: git, отдельная ветка на задачу, PR и ревью. Сообщения коммитов - по правилам выше,
связь с задачей - через `Closes #N` в описании PR.

Перед PR проверь изменение в локальной информационной базе и опиши проверку в «Как проверить».

## Pull request

- Одна задача - один PR.
- Заголовок - по правилам коммита и описывает весь PR целиком: он попадёт в merge-коммит.
- Описание - по шаблону, он подставляется сам. `Closes #N` закроет задачу при мерже.
- Нужен 1 approve. Ревьюер назначается автоматически.
- Мержит автор - после approve, когда все обсуждения закрыты.

Шаблон описания (`.github/pull_request_template.md`):

```markdown
Closes #

## Что сделано

-

## Как проверить

```

Пример:

```markdown
Closes #12

## Что сделано

- импорт расписания из CSV
- проверка формата: при ошибке - номер строки и причина

## Как проверить

Загрузить `data/cases/basic/input.csv` через «Импорт» - появятся 12 занятий.
Загрузить файл с пустой колонкой «Аудитория» - будет ошибка со строкой 3.
```

## Ревью

- Ответ - в течение суток: и ревьюеру на PR, и автору на замечания.
- Префиксы комментариев:
  - без префикса - нужно исправить;
  - `nit:` - мелочь, можно не исправлять;
  - `question:` - вопрос: ответь, менять код не обязательно.
- Обсуждение закрывает тот, кто его открыл: автор исправил и ответил, ревьюер проверил и закрыл.
