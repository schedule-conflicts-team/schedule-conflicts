## Краткая последовательность работы

1. [Открыть назначенную задачу и изучить требования](#1-открыть-или-создать-задачу).
   При появлении новой работы можно самостоятельно создать Issue и сообщить тимлиду.
2. [Создать ветку от свежего `main`](#2-обновить-main-и-создать-ветку).
3. [Выполнить задачу и сохранить изменения коммитами](#3-выполнить-задачу-и-создать-коммит).
4. [Перед PR обновить ветку относительно `main` и отправить её на GitHub](#4-обновить-и-отправить-ветку).
5. [Открыть PR по шаблону и дождаться ревью](#5-открыть-pr-и-дождаться-ревью).
6. [Если замечания есть, исправить их отдельными коммитами и отправить изменения](#6-исправить-замечания).
7. [После approve, когда все обсуждения закрыты, нажать Merge](#7-влить-pr).
   Ветка удалится сама, задача закроется через `Closes #N` в описании PR.
8. [Переключиться на `main` и обновить его](#8-обновить-локальный-main).

## Первоначальная настройка

Эти действия нужны при первом подключении проекта на компьютере. Для работы через SSH
ключ должен быть добавлен в аккаунт GitHub; для отправки изменений также нужны права
на репозиторий.

### Клонирование репозитория

Открыть Git Bash в папке, где будет храниться проект, и создать локальную копию:

```bash
git clone git@github.com:schedule-conflicts-team/schedule-conflicts.git
```

После завершения клонирования перейти в папку проекта:

```bash
cd schedule-conflicts
```

Если репозиторий уже склонирован, повторно клонировать его не нужно: открыть терминал
в существующей папке проекта. Если SSH запрашивает парольную фразу ключа, ввести её.
При ошибке доступа, например `Permission denied (publickey)`, обратиться к тимлиду.

### Имя и почта для коммитов

В папке проекта проверить, какие имя и почту использует Git:

```bash
git config user.name
git config user.email
```

Если значение не выведено или не подходит, выполнить соответствующую команду, заменив
текст в кавычках на имя или никнейм и адрес почты:

```bash
git config --local user.name "Имя Фамилия или никнейм"
git config --local user.email "адрес почты"
```

Флаг `--local` сохраняет настройки только для этого репозитория. Для проверки можно
повторить команды `git config user.name` и `git config user.email`.

Имя и почта попадают в коммиты и видны в публичном репозитории. Чтобы GitHub связывал
коммиты с аккаунтом, указать подтверждённую почту аккаунта или адрес GitHub `noreply`.
Адрес вида `ID+ник@users.noreply.github.com` можно найти в GitHub → Settings → Emails.

## Подробный цикл работы

В шаблонах команд значения в угловых скобках, такие как `<название-ветки>`,
нужно заменить данными задачи. Сами скобки `<` и `>` вводить не нужно.

Предполагается, что Git настроен, доступ к GitHub есть, а репозиторий уже склонирован.
Открыть терминал в папке репозитория. Например, можно открыть папку проекта в VS Code
и выбрать Git Bash во встроенном терминале. Перед командами обратить внимание на текущую
папку и ветку; ветку можно проверить командой `git status`. Если команда завершилась
с ошибкой, не переходить к следующему шагу до выяснения причины.

### 1. Открыть или создать задачу

Обычно задачи создаёт тимлид; он же назначает исполнителей. На GitHub открыть вкладку
**Issues**, найти назначенную задачу и прочитать её контекст, описание, критерии приёмки
и приложенные материалы. Если что-то непонятно, уточнить у тимлида.

Если обнаружена ошибка или появилась другая работа для проекта, любой участник может
создать Issue самостоятельно:

1. На вкладке **Issues** нажать **New issue**.
2. Указать название, контекст, что нужно сделать и критерии приёмки. Если нужны материалы,
   добавить ссылки на них.
3. Выбрать подходящие метки и тип задачи, если они доступны, и создать Issue. Сообщить
   тимлиду о новой задаче: исполнителя назначает он.

Так работа не потеряется: команда увидит, что нужно сделать, а описание и критерии
останутся в задаче. Через PR с ней можно будет связать выполненные изменения.

### 2. Обновить `main` и создать ветку

Перед переключением проверить текущую ветку и состояние файлов:

```bash
git status
```

Если остались незакоммиченные изменения, сначала разобраться с ними; при необходимости
обратиться к тимлиду. Затем переключиться на локальный `main`:

```bash
git switch main
```

Получить последние изменения с GitHub:

```bash
git pull --ff-only
```

Эта команда обновит `main` без создания коммита слияния. Если она сообщает о расхождении
истории, остановиться и обратиться к тимлиду.

Создать ветку для задачи. Шаблон:

```bash
git switch -c <название-ветки>
```

После команды проверить, что в терминале указана новая ветка. Правила названий - в разделе
[«Ветки»](#ветки). Для каждой задачи нужна отдельная ветка.

### 3. Выполнить задачу и создать коммит

Внести изменения в файлы проекта и проверить результат по критериям задачи. Для изменений 1С
также проверить результат в локальной информационной базе.

Посмотреть, какие файлы изменились:

```bash
git status
```

Добавить нужные файлы в индекс - набор изменений для следующего коммита. Шаблон:

```bash
git add <путь-к-файлу>
```

Если файлов несколько, указать их через пробел или добавить по отдельности. Путь с пробелами
заключить в кавычки. Повторить `git status` и проверить раздел **Changes to be committed**.
Затем посмотреть содержимое подготовленных изменений:

```bash
git diff --staged
```

Убедиться, что в коммит попадёт именно то, что нужно. Если просмотр открылся постранично,
нажать `q` для выхода.

Сохранить подготовленные изменения коммитом. Шаблон:

```bash
git commit -m "<тип>: <описание>"
```

Указать в сообщении тип и описание изменений. Формат и типы - в разделе
[«Коммиты»](#коммиты). При необходимости повторять подготовку файлов и создание коммитов по мере работы.

### 4. Обновить и отправить ветку

Оставаясь в ветке задачи, получить актуальный `main` и, если нужно, перенести коммиты задачи
поверх него:

```bash
git pull --rebase origin main
```

Если возник конфликт, остановиться и обратиться к тимлиду. Если ветка уже была отправлена
на GitHub и после обновления не получается отправить изменения, тоже обратиться к тимлиду.

При первой отправке указать название ветки задачи. Шаблон:

```bash
git push -u origin <название-ветки>
```

Флаг `-u` связывает локальную ветку с веткой на GitHub. В дальнейшем обычные новые
коммиты в эту ветку можно отправлять командой `git push`.

### 5. Открыть PR и дождаться ревью

На GitHub нажать **Compare & pull request** или открыть создание PR через вкладку
**Pull requests**. Заполнить заголовок и описание по шаблону: что сделано и как проверить.
В строке `Closes #<номер-задачи>` указать номер задачи.

Создать PR и проверить запрос ревьюера. Если ревьюер не назначен или долго не отвечает,
обратиться к тимлиду. Ревью проводит другой участник команды; подробнее - в разделе
[«Pull request»](#pull-request). Ревьюер проверяет изменения и сверяет их с критериями задачи.

### 6. Исправить замечания

Если ревьюер оставил замечания, сначала разобрать их с тимлидом. Внести исправления в той же
ветке, проверить изменения и создать отдельный коммит. Шаблон команд:

```bash
git status
git add <путь-к-файлу>
git diff --staged
git commit -m "<тип>: <описание-исправления>"
git push
```

Указать пути изменённых файлов и сообщение коммита. После `git push` существующий PR
обновится - новый создавать не нужно. Ответить в обсуждении и попросить повторно проверить исправление;
закрывает обсуждение тот, кто его открыл. Если замечаний нет, этот шаг с исправлениями
пропускается.

### 7. Влить PR

Когда PR одобрен другим участником с правами Write и все обсуждения закрыты, автор
нажимает **Merge pull request**, затем **Confirm merge**. Используется merge commit.
Проверить, что PR получил статус **Merged**, а связанная задача закрылась. Ветка на GitHub
удалится автоматически.

### 8. Обновить локальный `main`

Вернуться в локальный `main` и получить изменения с GitHub:

```bash
git switch main
git pull --ff-only
```

Теперь локальный `main` готов для начала следующей задачи.

## Справочник

### Типы веток и коммитов

Для веток и коммитов используется один набор типов. Тип ветки выбирают по задаче
в целом, а тип коммита - по конкретному изменению.

| Тип | Когда |
| ----- | ------- |
| `feat` | появилось что-то новое: функция, эндпоинт, экран, скрипт |
| `fix` | было неправильно, стало правильно (в коде, спеке или данных) |
| `docs` | только текст и документы |
| `refactor` | код переделан, поведение то же |
| `test` | тесты и контрольные примеры |
| `chore` | всё остальное служебное: конфиги, зависимости, CI, датасеты |

### Ветки

Формат: `тип/номер-задачи-описание`.

Правила:

- тип - один из [типов веток и коммитов](#типы-веток-и-коммитов);
- описание - латиницей, через дефис, 2-4 слова;
- одна ветка - одна задача.

Примеры:

```
feat/12-room-conflicts
fix/27-cancelled-lessons
docs/8-csv-format
```

### Коммиты

Формат: `тип: описание`.

Правила:

- тип - один из [типов веток и коммитов](#типы-веток-и-коммитов);
- описание - в инфинитиве: «добавить», «исправить», а не «добавил» или «добавлена»;
- описание - со строчной буквы, без точки в конце;
- вся первая строка - не длиннее ~72 символов;
- тело - только если из заголовка и диффа непонятно, **зачем** сделано изменение;
  указать причину, а не пересказ диффа;
- между заголовком и телом - пустая строка;
- каждый коммит ветки попадает в `main` и пишется по этим правилам;
- правки по ревью - отдельный коммит, тоже по этим правилам.

Примеры:

```
feat: добавить импорт расписания из CSV
fix: не учитывать отменённые занятия при поиске конфликтов
fix: учитывать пустые строки в CSV
docs: описать формат CSV для импорта
refactor: вынести проверку конфликтов в отдельный модуль
test: добавить контрольный пример с двойным бронированием аудитории
chore: добавить .editorconfig
```

Пример коммита с телом:

```
fix: не учитывать отменённые занятия при поиске конфликтов

Отменённое занятие оставалось в выборке и блокировало аудиторию:
УО не мог поставить замену в освободившийся слот.
```

### Pull request

Формат: заголовок `тип: описание` и описание по шаблону.

Правила:

- одна задача - один PR;
- заголовок - по [правилам коммитов](#коммиты), описывает весь PR целиком и попадёт в merge-коммит;
- описание - по шаблону, он подставляется сам;
- `Closes #N` - закроет задачу при мерже;
- ревью - нужен 1 approve, ревьюер назначается автоматически;
- мерж - выполняет автор после approve и закрытия всех обсуждений.

Шаблон описания (`.github/pull_request_template.md`):

```markdown
Closes #

## Что сделано

-

## Как проверить

-
```

Пример:

```markdown
Closes #12

## Что сделано

- импорт расписания из CSV
- проверка формата: при ошибке - номер строки и причина

## Как проверить

Загрузить `data/cases/basic/input.csv` через «Импорт» - появятся 12 занятий.
Загрузить файл с пустой колонкой «Аудитория» - будет ошибка со строкой 3.
```
